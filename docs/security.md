# Security

Two secrets, TLS you control, encryption you can restore with, and a port list you can defend.

## The API secret

Every API request that touches data or the cluster carries the API secret as a bearer token:

```bash
curl -H "Authorization: Bearer $SECRET" http://10.0.0.1:8200/cluster/membership
```

One shape is accepted. A raw secret without the `Bearer ` scheme is refused with a message that
tells you to send it as a bearer token. Your `Client` does this for you; the only place you write
it by hand is `curl`.

`secret_api` is a shared secret for the whole cluster. Minimum 16 characters, and different from
`secret_raft`.

What the API secret authenticates: the query endpoints, the streams, `/listen`, `/backup`, and
everything under `/cluster`.

What runs without it: `/health`, `/ready`, `/ping`, `/version`. Those answer "is this node alive and
usable" and nothing else. Put them on a network you trust, and do not treat them as a status
endpoint you can expose to the internet.

The dashboard is its own login, with its own password, and it works with the `sqlite` feature.

## Keeping secrets out of logs

The secret is in a standard `Authorization` header, which the common proxies, log collectors, and
client libraries already treat as sensitive. That is the reason the header is `Authorization`: your
existing log redaction covers it.

Where secrets still leak: your own request logging middleware, shell history, `curl -v` output,
crash dumps, and a config file in a git repo. Use `secrets_file` with `$SECRETS` so the reviewable
config contains no values, and mount secrets the way your platform does it. See `configuration.md`.

## Rotating secrets

Rotate `secret_api` as a cluster operation: it authenticates every node to every other node's API.
Stop the nodes, set the new value on all of them, start them. A cluster whose members disagree on
the secret cannot authenticate, and the failure looks like an auth error on every request.

`secret_raft` rotates the same way. It authenticates cluster traffic on the Raft port.

## The Raft port

The Raft port carries cluster traffic only. It must be reachable between nodes and unreachable from
everything else. A network policy, a firewall rule, or a private interface: pick one, and make it
explicit in the deployment.

The API port carries your clients. Expose it to the things that need it, and nothing more.

## TLS

- `tls_auto_certificates` - self-signed certificates generated by the node, with client
  verification off. It is encrypted, mutually authenticated traffic with no PKI, which is the right
  default inside a private network and the wrong answer on a shared one: an endpoint that can spoof
  a node can capture your API secret. On any network you do not own, use real certificates.
- `tls_raft_key` / `tls_raft_cert` and `tls_api_key` / `tls_api_cert` - your own certificates, key
  and certificate together.
- `tls_raft_danger_tls_no_verify` / `tls_api_danger_tls_no_verify` - accept certificates you did
  not issue. The names say it. Testing and self-signed setups only.
- `webpki-roots` - baked-in root certificates, for a minimal container with no OS trust store.
- TLS is per port. Securing the Raft port and leaving the API port plain HTTP is a real
  configuration you can ship. Check both.

## Backup encryption

Backups are encrypted with `enc_keys`, and `enc_key_active` picks the key new backups use.

- A backup is unreadable without the key that made it.
- Rotating the key does not lock you out, as long as the old key stays listed in `enc_keys`.
- Remove an old entry only after the last backup made with it is gone.
- These keys are not in your database and not on your volume. Keep them somewhere that survives the
  cluster, because a restore needs them.
- S3 credentials are secret material too. Give the node only the bucket it writes to.

## Data at rest

The database file on your volume is a plain SQLite file, and the local backup files are encrypted
with your encryption keys. Volume-level encryption, disk access control, and backups off the node
are yours to provide. Hiqlite gives you replication, not confidentiality of the volume.

## Statements in logs

`log_statements` logs the SQL your cluster applies, including the statements that contain user
values. It is a debugging tool with a data-leak surface. Turn it on for hours, and never in a
system whose logs are broader than your database.

## Rate limits are not a security control

They exist so a saturated disk cannot make a healthy cluster look dead. They bound your own load,
not an attacker's. If you need to limit who can write, do it in your app, in front of the API port.

## What is not here

- One shared API secret per cluster, not per-user database credentials. Authorization is your app's
  job.
- No row-level security, no column encryption, no audit trail.
- No OS-level privilege separation between the node and your app: they are the same process when you
  embed Hiqlite, so it runs with your app's privileges.
